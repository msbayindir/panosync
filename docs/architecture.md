# Architecture

This document describes how panosync works: its components, how data flows between them, the
**v1 protocol** (message format and key derivation) and the threat model.

## Components

```
 device A (panosync)                 relay (panosync-relay)                device B (panosync)
┌─────────────────────┐            ┌────────────────────────┐            ┌─────────────────────┐
│ clipboard thread    │            │ /ws?channel=<id>       │            │ clipboard thread    │
│  poll every 400 ms  │            │  groups connections by │            │  writes received    │
│        │  ▲         │            │  channel id, forwards  │            │  text to clipboard  │
│        ▼  │ mpsc    │   wss://   │  each binary message   │   wss://   │        ▲  │         │
│ network task        │ ─────────► │  to the other devices  │ ─────────► │ network task        │
│  seal / open (v1)   │ ◄───────── │  of the channel        │ ◄───────── │  seal / open (v1)   │
└─────────────────────┘            │ /health → "ok"         │            └─────────────────────┘
                                   └────────────────────────┘
```

| Component | Code | Responsibility |
|---|---|---|
| CLI | `client/src/cli.rs`, `client/src/main.rs` | parses commands (`setup`, `start`, `key`, `config`, `pause`) and runs them |
| Config | `client/src/config.rs` | locates the config directory, reads and writes `config.toml` |
| Clipboard loop | `client/src/clipboard.rs` | polls the OS clipboard on a dedicated thread, detects local changes, applies incoming text, prevents echo, honours `pause` |
| Pause | `client/src/pause.rs` | the `paused_until` state file |
| Network | `client/src/net.rs` | WebSocket connection to the relay, keep-alive pings, reconnection with backoff |
| Protocol | `client/src/protocol.rs` | the encrypted payload and the checks on incoming messages |
| Crypto | `client/src/crypto.rs` | key derivation and XChaCha20-Poly1305 sealing |
| Relay | `relay/src/lib.rs`, `relay/src/main.rs` | stateless WebSocket fan-out with limits |

The clipboard thread and the network task talk through two bounded `tokio::sync::mpsc`
channels (16 entries each). Clipboard APIs are blocking and some platforms want them on one
thread, so they stay out of the async runtime.

## Data flow

**Sending (device A)**

1. Every 400 ms the clipboard thread reads the clipboard text.
2. If it differs from the last text seen or written, it is remembered, and then:
   - if a pause is in effect (`paused_until` is in the future), it is not sent;
   - if it is larger than 512 KiB, it is not sent;
   - otherwise it goes to the network task. If the queue is full, the copy is skipped.
3. The network task builds a payload, seals it (see below) and sends it as one binary WebSocket message.
   Changes queued while disconnected are collapsed: after reconnecting only the most recent one is sent.

**Relaying**

4. The relay forwards the bytes unchanged to every other connection on the same channel.

**Receiving (device B)**

5. The network task opens the message and validates it (see *Checks on incoming messages*).
6. Valid text goes to the clipboard thread, which writes it to the clipboard and remembers it as
   the last text, so that the next poll does not treat it as a new local copy and send it back.

Clipboard contents are never logged; log lines contain byte counts only.

## v1 protocol

### Master key

A random 32-byte value generated by `panosync setup` on the first device (OS random number
generator), shown to the user as **unpadded URL-safe base64** (43 characters). All devices of a user
share it. It is stored in `config.toml` as `key`.

### Key derivation

Two values are derived from the master key with BLAKE3 in key-derivation mode
(`blake3::derive_key(context, master_key)`):

| Value | Context string | Use |
|---|---|---|
| encryption key (32 bytes) | `panosync v1 encryption key` | XChaCha20-Poly1305 key |
| channel id (32 bytes, sent as 64 lowercase hex chars) | `panosync v1 channel id` | tells the relay which devices belong together |

Different contexts give independent outputs, so the channel id reveals nothing about the
encryption key or the master key.

**Test vector.** For a master key of 32 bytes all equal to `0x07`
(base64 `BwcHBwcHBwcHBwcHBwcHBwcHBwcHBwcHBwcHBwcHBwc`), the channel id is
`5c08f796719c0a8c00c0a4ad475932a56bac3d55d5491d8a9823475c80519236`.
This is pinned by the `v1_derivation_is_stable` test and was cross-checked with the Python `blake3` package.

### Connection

```
GET /ws?channel=<64 lowercase hex chars>   (WebSocket upgrade, wss:// in production)
```

The relay rejects any other channel format with `400 invalid channel`. All application messages
are **binary** WebSocket messages. Clients send a WebSocket ping every 25 seconds and treat 70
seconds without any frame from the relay as a dead connection.

### Sealed message

```
offset  size  field
0       1     protocol version = 0x01
1       24    nonce (random, XChaCha20)
25      n+16  ciphertext of the payload, followed by the 16-byte Poly1305 tag
```

- Algorithm: XChaCha20-Poly1305 (IETF AEAD with 24-byte nonce), key = the derived encryption key.
- Associated data: the ASCII string `panosync v1`.
- A fresh random nonce is generated for every message; with 192-bit nonces random generation is safe.
- Messages shorter than 41 bytes, with another version byte, or failing authentication are rejected.

### Payload

The plaintext is a UTF-8 JSON object:

```json
{"v":1,"device":"3f9c0b2a7d1e4c55","id":12872310044551902117,"time":1794787200,"text":"ssh deploy@10.0.0.5"}
```

| Field | Type | Meaning |
|---|---|---|
| `v` | integer | protocol version, must be `1` (also authenticated, unlike the header byte alone) |
| `device` | string | random 64-bit id of the sending process, 16 hex chars, new on every start |
| `id` | integer (u64) | random message id |
| `time` | integer | sender's Unix time in seconds |
| `text` | string | the clipboard text |

### Checks on incoming messages

A message is accepted only if, in this order:

1. it decrypts and authenticates with the encryption key, and both version fields are `1`;
2. `device` is not this process's own id (otherwise it is silently ignored: echo through the relay);
3. `time` is within **300 seconds** of the local clock, in either direction;
4. `id` is not among the last **512** ids accepted by this process (replay);
5. `text` is at most **512 KiB**.

### Relay limits

| Limit | Value |
|---|---|
| message size (sealed) | 1 MiB |
| devices per channel | 16 |
| messages per connection | 50 per 10 seconds; the connection is closed when exceeded |
| buffer per channel | 32 messages; slow receivers skip messages rather than block others |

### Versioning rule

**Anything that changes the bytes on the wire or the key derivation must increase the protocol
version**: the header byte, the `v` field, and the version inside the context strings and the
associated data (`panosync v2 …`). A client only accepts messages of its own version. This includes
renaming payload fields, changing the encoding, changing the AEAD or the KDF contexts. Changes the
other side cannot observe (log messages, polling interval, relay limits) do not need a new version.

## Threat model

**Assets:** the clipboard text, and the master key that protects it.

**What panosync protects against**

| Adversary | Protection |
|---|---|
| The relay operator (or whoever compromises the relay) | cannot read or undetectably modify text: end-to-end AEAD with a key the relay never sees |
| A network observer | TLS (`wss://`) on top of the end-to-end encryption |
| Someone who does not know the key, connecting to the relay | cannot join a channel without guessing a 256-bit derived value; cannot forge messages |
| Replays by the network or the relay | random message ids remembered per process, 5-minute time window |
| Other local users on macOS/Linux | `config.toml` is created with mode `600` |
| Abuse of a public relay | message size, devices-per-channel and rate limits |

**What it does not protect against (known limitations)**

- **Metadata.** The relay sees client IP addresses, when messages are sent, their sizes (which reveal
  the approximate text length) and the channel id. The channel id is stable, so it links a user's
  devices and sessions over time.
- **A compromised device.** Any device holding the master key can read all traffic. There is one
  shared static key: no forward secrecy (recorded traffic can be decrypted if the key leaks later)
  and no per-device revocation. Recovery: generate a new key and set up every device again.
- **Availability.** The relay can drop or delay messages. Within the 5-minute window it can replay a
  recent message to a client that has restarted since, because seen ids are kept in memory only.
- **Sensitive clipboard content.** Everything copied is synced, including passwords. There is no
  detection of password-manager copies yet; `panosync pause <minutes>` is the manual control.
- **Clock skew.** Devices more than 5 minutes apart in time reject each other's messages.
- **Windows file permissions.** panosync does not set ACLs on Windows; the config file inherits the
  user profile's permissions (see the README).
- **The local machine.** Malware running as the user can read the clipboard and the config file anyway.
